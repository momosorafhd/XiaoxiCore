# 架构、扩展与验收

## 一条私聊如何完成

1. `message_bridge`（消息桥）接受 OneBot 反向 WebSocket，只接纳与配置的机器人、主人和私聊类型一致的输入。它把平台消息编号、时间、消息段和来源交给 `assistant`（助手）。启动补收和实时消息最终走同一接纳路径。
2. 助手写入本实例的 SQLite 状态，按会话顺序调度。角色模块生成当前场景的提示，模型设置模块选择日常、整理或工作的绑定。助手把本轮交给 `dsh_bridge`（Core 侧模型桥），由 DSH 插件创建或恢复属于本实例的会话。
3. 模型调用图书馆或任务工具时，DSH 插件回调本机 `/api/bridge/tool`。Core 校验机器令牌和会话类型，执行搜索、读取或写入，结果回到下一次模型请求。图书馆默认关键词检索，向量搜索需另外提供匹配的编码器环境和模型。工具的实际使用频率由所选模型决定。
4. 独立工作在自己的会话执行，完成后向日常会话回交结果摘要。日常会话可分页读全文或产物。正常聊天结束时，消息桥再次核对原渠道和收件人，发回文本并记录回执。停机补收依赖助手已接纳的编号，跨页时还需确认 SnowLuma 的索引锚点。

## 改动从哪里开始

| 需求 | 代码与实现约束 |
| --- | --- |
| 加一种插件 | 以 [示例插件](../plugins/example/plugin.py) 和 [清单](../plugins/example/plugin.json) 为起点，定义 `requires`、配置校验和启停。通过 `context.services.provide/get` 发布或取得服务；HTTP 与事件登记随实例撤销。线程、端口和连接必须能在插件卸载时清理。 |
| 新增消息渠道 | 参考 [消息桥](../plugins/message_bridge/plugin.py)。需要定义稳定的渠道与联系人标识、消息编号、顺序、相同消息的重投、发送结果不确定及历史覆盖。图库和助手共用本实例数据，多用户产品需要另做会话、记忆、令牌与管理权限隔离。 |
| 换模型宿主或 DSH 版本 | Core 侧适配器与宿主内插件是接口两端。需要核对会话创建/恢复、工具回填、取消和能力探测。高级提示补丁会核验宿主文件哈希。[DSH 版本与补丁](DSH.md) |
| 改角色、整理、记忆 | 用户日常编辑用管理台。新增注入点要说明在建会话、当前轮、任务回交或按日整理中的哪个时机生效。修改归档时保留消息来源、时间与版本校验。 |
| 改管理台或启用其他系统 | 管理台静态文件与模板在 `packages/xixi-core/xixi_core/modules/console`。资源监控读取 Linux 的 `/proc`、`/sys`，不同硬件的可用指标不同。Windows 的文件权限、锁、IPC、宿主插件及资源监控需要部署者自行验证。 |

## 可复现的检查

在根目录用已安装锁定依赖的 Python 执行平台测试。测试使用临时 SQLite、虚构账号和回环连接。Node 测试覆盖 DSH 插件契约与可选网页插件。在 Linux 上安装了 Nginx、OpenSSL 时可额外验证两个站点样例从登录到退出的实际代理流程。

```sh
.venv/bin/python -m unittest discover -s tests -p 'test_platform*.py'
node --test packages/xixi-bridge/test/existing-dsh.test.mjs integrations/owner-sso/plugin.test.mjs
.venv/bin/python scripts/verify_lan.py
```

要检查真实 DSH 进程加载本仓库插件、模型请求中的提示和图书馆工具的返回，运行 [隔离 DSH 联调](DSH.md)。这使用本机合成模型。接上部署者的真实 QQ 和模型后，再记录一条主人私聊、非主人消息被过滤和一次停机补收的实际结果。
